# Blind spot log

- Byte-consumption ownership: skipped `*` in both main.rs and findArraySize (double-skip → array size parsed as 0); earlier, findArraySize left its trailing `\r\n` unconsumed. Underlying gap: no fixed convention for which function consumes which bytes of the input.
- Bounds check ANDed into the terminator-match condition in both findArraySize and parseString, so running out of input means "never break" instead of "stop parsing." Underlying gap: treats the bounds guard as part of the content check rather than as its own loop-exit condition.
- Debugged the same boundary condition by cycling operators (`<`, `>`, `==`) across three edits without tracing an input through the loop. Underlying gap: mutating code before simulating it by hand; conditions treated as slot machines.
- Wrote Rust constructs by shape without semantics: `match` on a bool with `True`/`False` arms, bare `Result` as an if-body statement, `Err(False)`. Underlying gap: type vs. value distinction; `match` earns its keep destructuring enums, not dispatching on bools.
- Fused the protocol layer into the command layer twice in one file: `RespProtocolDataType` whose variants were `PING`/`ECHO`, and `parseString` calling `PINGCommand`/`ECHOCommand` mid-parse. Underlying gap: a function that returns `()` has nowhere to put its result, so the work migrates inward; decide what a stage *returns* before writing its body.
- Solved "read a decimal length terminated by CRLF" correctly in `findArraySize`, then hand-rolled a single-digit broken version of the same subproblem 50 lines later in `parseString`. Underlying gap: doesn't recognize a repeated subproblem as a call site; reaches for a fresh inline implementation instead of the function already written above.
- Reached for a struct field (`bytes_vec`) to hold per-call accumulator state, twice: once in the original design, again when reasoning it through with recursion on the table. Justified it with "a local wouldn't survive Rust's lifetime rules." Underlying gap: (a) lifetimes govern references, not owned values — a local `Vec` leaves a function by being moved; (b) no instinct for "how many of these are live simultaneously?" as the test for field vs. local. Recursion means N in flight, and the call stack is already the stack you need.
- Collapsed the encode layer into the command layer: proposed a separate enum per command, each carrying an already-encoded `Vec<u8>`, while in the same breath saying "idk what dispatch will return." Third instance of layer fusion. Underlying gap: reaches for the return type of the *last* stage and lets it propagate backward into every stage before it, instead of asking "what do all the commands have in common?" and naming that one type once.
- Trailing `;` silently discarded the value of an expression, twice in a row: first as the statement-position `match` in main.rs, then — immediately after that was pointed out — reproduced one scope inward on the `Ok` arm's body, so the outer `let` bound `()` instead of the `Result`. Underlying gap: reads `;` as end-of-line punctuation (C# habit) rather than as the thing that turns an expression into a statement and throws its value away. Test to apply: "what does this block evaluate to?" — not "is this line complete?"
- Indexed `content.get(1)` for the command name (it is element 0) and guarded it with `len() > 1`, so every command — bare `PING` included — fell through to the error arm. The same wrong index appears in both the live version and the commented-out one, so it was never traced even once. Underlying gap: repeat of writing an index/boundary condition without hand-simulating one concrete frame through it first.
- Reverted the payload-carrying `Command` variants back to bare ones, reasoning that extracting the arguments was "part of the dispatch work." Extracting arguments is exactly what the conversion layer is for. Fourth instance of layer misattribution — this time deciding a layer owns too *little* rather than too much, which produced a plan to pass both the `Command` and the original `RespProtocolDataType` into dispatch.
- Hit a borrow-check conflict (moving `content` into a `Command` variant while a reference obtained from `content.get(0)` was still live) and responded by commenting out the payload-carrying design and keeping empty variants that compile but throw the arguments away. Underlying gap: reads a borrow error as a verdict on the design rather than a question about *ordering* — the fix is almost always to finish reading before moving, not to abandon the type that holds the data.
- Called a method for its side effect and discarded its return value, twice in two edits: `content.into_iter();` and `content_iter.next();`, then reached for the receiver as if it had been updated in place. Underlying gap: C# collection methods mostly mutate and return void (`List.Add`, `List.Sort`), so "call it and the object is now different" transfers wrongly to Rust, where the return value usually *is* the result. Ask what a method hands back before writing the semicolon.
- Introduced a new traversal (`content.iter()` + `next()` to take the command name) while leaving the old index-based code (`content.len()`, `content.get(0)`) in place below it, so the two disagreed about whether the command name had been consumed — the same off-by-one returned in a new costume. Underlying gap: migrates the top of a function to a new mechanism and leaves the bottom on the old one; no habit of asking "who has consumed what by this line?" after changing the data flow. Same family as the original byte-consumption entry.
- Collapsed the encode layer into the command layer again, this time in code: `ping_command`/`echo_command` build `$2\r\nhi\r\n` with `format!` and store the framed bytes *inside* `RespProtocolDataType::BulkStrings`, while the parser stores the unframed payload in that same variant. Fifth instance of layer fusion, with a new failure mode attached: one enum variant made to mean two different things depending on which direction the data is flowing, so parse and encode are no longer inverses and `Arrays` becomes unencodable. Underlying gap: treats an enum as a bag to carry bytes to the next function rather than as a statement about what the value *is*. Test to apply: parse X, re-encode it, do you get X back?
- Migrated one arm of a `match` to the new contract and left the sibling arm on the old one: `ping_command`'s `Some` arm became `BulkStrings(val)` (unframed value, correct) while the `None` arm kept `SimpleStrings(b"+PONG\r\n")` (framed bytes, the thing being removed) — two arms of one expression now disagreeing about what the enum holds. Direct repeat of the earlier partial-migration entry, at the tightest possible scope. Underlying gap: applies a fix at the site that prompted it rather than re-reading every construction site of the type under the new rule. After changing what a type means, grep for every place it is built.
- Superseded code left commented out in place rather than deleted (`ping_command`, `echo_command` each now carry a dead copy of the old framing version). Third occurrence of this habit, and it has already cost once: the earlier command-name index bug existed identically in the live and commented-out copies, which is how it survived unnoticed. Underlying gap: treats the file as the undo history. Git already holds the old version; two versions in one file only create the chance for them to disagree.
- Moved the framing code from `respdispatcher.rs` into the new `encoder.rs` and carried the `format!` + `String::from_utf8_lossy` bug along with it verbatim — the same length-prefix/byte-count desync that was identified and deleted from those exact lines an hour earlier. Underlying gap: relocating code is done by transplant, not by rewriting against the current understanding; the old text is trusted because it is already written. When a function moves layers, re-derive its body from what it is now supposed to guarantee.
- `format!` + `String::from_utf8_lossy` for assembling wire bytes, second occurrence: removed from `ping_command`/`echo_command` on request, then rewritten verbatim one layer down in `respencoder.rs` — including the same `msg.len()` / lossy-byte-length desync that corrupts the framing for any non-UTF-8 payload. Underlying gap: `format!` is the reflex for "build a thing out of parts" because C# string interpolation was, so byte assembly gets routed through a text type that has no business touching binary data. Cue to catch it: the moment `String` appears anywhere between a `Vec<u8>` and a socket, stop.
- Reintroduced the `format!` + `String::from_utf8_lossy(&msg)` + `msg.len()` length-desync bug verbatim in `respencoder.rs` after removing it from `ping_command`/`echo_command` for that exact reason one step earlier. Underlying gap: heard "this belongs in the encoder, not the handler" and moved the code, without hearing "this code is wrong." A correction about *where* something lives does not retract the correction about *what it does*; when relocating code that was just criticized, re-apply the criticism at the new site. Related: no instinct yet for staying in `Vec<u8>` — reaches for `format!` (a text tool) any time bytes need assembling.
- Chained `b"$".to_vec().extend_from_slice(..)` and bound the result to a variable, expecting the `Vec` back; `extend_from_slice` returns `()`. This is the mirror of the earlier `content.into_iter();` / `content_iter.next();` entry — that time a returning method was treated as mutating, this time a mutating method is treated as returning `Self`. Underlying gap is one thing, not two: writes the expression before checking whether the method hands back `Self`, a new value, or `()`. C#/LINQ trains both habits at once (`List.Add` mutates and returns void; `IEnumerable.Where` returns a new sequence) and the distinction is carried by convention there, by the signature here. Read the return type before chaining or binding.
- Predicted the temporary-lifetime pair backwards: said `let digits = n.to_string().as_bytes();` compiles ("it's returning the vec<u8> and binding it") and that `out.extend_from_slice(n.to_string().as_bytes())` does not. Both halves are wrong, and the stated reason shows the cause — read `as_bytes()` as producing an owned `Vec<u8>` when it returns a borrowed `&[u8]`. Second instance of conflating owned values with borrows (cf. the `bytes_vec` field-vs-local entry: "lifetimes govern references, not owned values"). Underlying gap: no habit of asking "does this expression hand me the thing, or a view of the thing?" before deciding what a binding keeps alive. Rule to internalize: a name keeps an *owned* value alive; a name on a *borrow* does not keep its owner alive.
